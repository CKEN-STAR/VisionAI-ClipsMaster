# 根因修复：LLM SRT解析失败 → JSON约束生成 + 解析器容错

时间：2025-11-07
负责人：Augment Agent

## 背景
- 日志显示：本次 UI 完整流程中，第1/2/3/5/6批均出现“AI解析失败，使用规则引擎生成SRT格式”，表明LLM直出SRT在多批次不稳定。
- 目标：从根源降低解析失败概率，优先让LLM按结构化格式输出，必要时保持现有兜底。

## 根因
- LLM在长上下文/批处理场景中，容易输出解释性语句或非标准SRT行（如“1. …”、“观察每个句子…”），导致严格SRT解析`int()`/时间轴正则失败。
- 清洗器移除了大量非SRT内容，导致“清理后响应为空”，进而触发回退。

## 方案与取舍
- 方案A（已实施）：JSON模式约束生成 + 解析器容错
  - 为“分批混剪”新增JSON提示词；先走`json_only=True`生成并解析；失败再回退到SRT提示词与解析；再失败走规则引擎。
  - 在SRT解析器中放宽“序号行”解析（接受“1.”、“1、”）。
  - 优点：改动小、风险低、向后兼容；日志可见性更好。
  - 缺点：仍依赖模型质量；若JSON也不合规，会回退（有兜底）。
- 方案B（未实施，可选）：llama.cpp GBNF语法约束SRT
  - 通过grammar强约束输出形态。
  - 需在`create_completion`配置grammar，改动略大；暂不做。

## 代码改动
文件：src/core/real_ai_engine.py
- 新增：
  - `_build_batch_merge_prompt_json(...)`
  - `_parse_batch_mixed_cut_subtitles_json(...)`
- 调整：
  - 在`generate_viral_subtitle_batch()`的分批循环中，优先尝试JSON模式→解析；若空则回退SRT→解析；仍空则沿用原“规则引擎”兜底。
  - 在`_parse_batch_mixed_cut_subtitles()`中，序号解析由`int(lines[0].strip())`改为正则提取首个数字，容错`1.`/`1、`等。

## 预期日志新增
- `第N批(JSON)响应长度: ...`
- `第N批(JSON)：成功解析 X 条混剪字幕`
- 回退路径：`第 N 批：JSON模式未产出，回退至SRT解析`

## 风险与回滚
- 风险：极低。未更改原有兜底与时轴重建；仅新增优先路径与小幅容错。
- 回滚：将新增函数删除，并还原分批循环与序号解析行即可。（已在git可回滚）
