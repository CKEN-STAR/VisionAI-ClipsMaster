   - 用途：方便用户手动管理文件

#### ❌ **未实现的功能**

1. **GGUF版本管理**
   - 原因：GGUF模型没有版本管理系统（没有`versions.json`）
   - 影响：无法"激活"特定的GGUF版本
   - 现状：系统自动选择最新的GGUF文件用于推理

2. **GGUF版本切换**
   - 原因：推理引擎会自动选择最新的GGUF文件
   - 代码位置：`src/core/real_ai_engine.py`
   - 逻辑：按文件修改时间排序，选择最新的

3. **GGUF性能对比**
   - 原因：性能评估只针对HuggingFace格式的训练模型
   - 影响：无法在UI中直接对比不同量化类型的性能
   - 替代方案：用户需要手动测试不同GGUF模型

### 架构设计差异

#### HuggingFace模型（训练轨道）
```
models/qwen/finetuned/
├── version_20251024_120000/
│   ├── config.json
│   ├── adapter_config.json
│   └── adapter_model.safetensors
└── versions.json  ← 版本管理文件
```

**特点**：
- ✅ 完整的版本管理
- ✅ 可以激活/切换版本
- ✅ 记录训练参数和性能
- ✅ 支持多版本保留

#### GGUF模型（推理轨道）
```
models/qwen/quantized/
├── trained_20251024_120000_Q4_K_M.gguf
├── trained_20251025_150000_Q5_K.gguf
└── trained_20251025_210201_Q4_K_M_f16.gguf
```

**特点**：
- ❌ 没有版本管理文件
- ❌ 只是简单的文件列表
- ✅ 文件名包含时间戳和量化类型
- ✅ 推理时自动选择最新文件

### 功能对比表

| 功能 | HuggingFace模型 | GGUF模型 |
|------|----------------|----------|
| 查看列表 | ✅ | ✅ |
| 查看详情 | ✅ | ✅ |
| 激活版本 | ✅ | ❌ |
| 版本切换 | ✅ | ❌ |
| 性能评估 | ✅ | ❌ |
| 删除模型 | ✅ | ✅ |
| 打开文件夹 | ✅ | ✅ |
| 转换为GGUF | ✅ | N/A |

### 使用建议

1. **保留多个GGUF版本进行对比**
   - 转换不同量化类型的GGUF模型
   - 手动测试推理效果
   - 删除不满意的版本

2. **通过文件名识别版本**
   - 格式：`trained_{时间戳}_{量化类型}.gguf`
   - 示例：`trained_20251025_210201_Q4_K_M_f16.gguf`
   - 最新的文件会被自动使用

3. **定期清理旧版本**
   - GGUF文件体积较大（2-3GB）
   - 保留2-3个最佳版本即可
   - 使用"删除GGUF"功能清理

self.supported_quant = {

### 量化类型详解

#### 1. **K-quants系列**（推荐）

| 类型 | 位数 | 文件大小 | 质量 | 推荐场景 |
|------|------|----------|------|----------|
| Q2_K | 2-bit | ~0.8GB | ⭐⭐ | 极限压缩，测试用 |
| Q4_K_S | 4-bit | ~1.2GB | ⭐⭐⭐ | 小体积，质量可接受 |
| Q4_K_M | 4-bit | ~1.5GB | ⭐⭐⭐⭐ | **推荐**，平衡质量和体积 |
| Q5_K_S | 5-bit | ~1.8GB | ⭐⭐⭐⭐ | 高质量，体积适中 |
| Q5_K | 5-bit | ~2.0GB | ⭐⭐⭐⭐⭐ | 高质量 |
| Q6_K | 6-bit | ~2.4GB | ⭐⭐⭐⭐⭐ | 接近原始质量 |

**特点**：
- 使用混合量化策略
- 不同层使用不同的量化精度
- 重要层（如注意力层）使用更高精度
- 需要两步转换：HF → F16 GGUF → K-quants GGUF

#### 2. **普通量化**

| 类型 | 位数 | 文件大小 | 质量 | 推荐场景 |
|------|------|----------|------|----------|
| Q8_0 | 8-bit | ~2.8GB | ⭐⭐⭐⭐⭐ | 高质量，体积较大 |

**特点**：
- 统一量化所有层
- 质量稳定
- 体积较大

#### 3. **浮点格式**

| 类型 | 位数 | 文件大小 | 质量 | 推荐场景 |
|------|------|----------|------|----------|
| F16 | 16-bit | ~3.0GB | ⭐⭐⭐⭐⭐⭐ | 原始质量，作为中间格式 |
| BF16 | 16-bit | ~3.0GB | ⭐⭐⭐⭐⭐⭐ | Brain Float，训练友好 |
| F32 | 32-bit | ~6.0GB | ⭐⭐⭐⭐⭐⭐ | 完整精度，体积巨大 |

**特点**：
- 保持原始精度
- 体积大
- F16常用作K-quants的中间格式

### 为什么选择Q4_K_M和Q5_K？

#### 当前选择的理由

1. **Q4_K_M（中文模型）**
   - ✅ 质量和体积的最佳平衡
   - ✅ 文件大小适中（~1.5GB）
   - ✅ 推理速度快
   - ✅ 质量损失可接受（<5%）

2. **Q5_K（英文模型）**
   - ✅ 更高的质量（英文模型通常更大）
   - ✅ 文件大小可接受（~2.0GB）
   - ✅ 质量损失很小（<3%）

#### 问题

- ❌ 用户无法根据自己的需求选择
- ❌ 没有考虑用户的硬件限制（内存、存储）
- ❌ 没有考虑用户的质量要求
- ❌ 不是"智能选择"，而是"开发者预设"

#### 方案2：智能推荐 + 手动选择

根据模型大小和用户硬件自动推荐：

```python
def recommend_quantization(model_size_gb, available_memory_gb):
    if available_memory_gb < 4:
        return "Q2_K"  # 低内存设备
    elif model_size_gb > 5:
        return "Q4_K_M"  # 大模型
    elif available_memory_gb > 16:
        return "Q6_K"  # 高端设备
    else:
        return "Q4_K_M"  # 默认推荐
```

**优点**：
- ✅ 真正的"智能选择"
- ✅ 考虑硬件限制
- ✅ 用户仍可手动覆盖

- ✅ 可以查看、删除GGUF模型

- ❌ 用户无法选择量化类型
